# Collaboration Bot — Product Requirements Document

- Статус: `Approved for solo launch`
- Версия: `0.3`
- Дата: `2026-08-25`
- Первый рынок: Екатеринбург
- Язык MVP: русский

## 1. Назначение и источник истины

Этот документ является каноническим продуктовым контрактом MVP Telegram-бота для поиска партнёров по коллаборациям.

[Исходное ТЗ](../tz_telegram_collaboration_bot.md) сохраняется как discovery-документ: он объясняет происхождение идеи и перечисляет возможные направления развития, но не определяет обязательный scope реализации.

При противоречии источники применяются в следующем порядке:

1. этот PRD;
2. `docs/TECHNICAL_DESIGN.md`;
3. исходное ТЗ.

Изменение продуктовой политики сначала вносится в PRD, а затем отражается в Technical Design и тестовой трассировке.

## 2. Контекст и проблема

Локальным блогерам, Telegram-каналам, заведениям и брендам сложно системно находить друг друга для взаимовыгодного продвижения. Предложения распределены по личным сообщениям и чатам, условия описываются каждый раз заново, а автору трудно собирать и сравнивать отклики.

Первый запуск проверяет только то, могут ли несколько приглашённых вручную людей пройти основной цикл:

`профиль → предложение → обнаружение → отклик → решение автора → контакт`.

Продукт не проводит саму коллаборацию и не гарантирует выполнение договорённостей. После принятия отклика стороны общаются напрямую.

## 3. Цель и гипотеза MVP

### 3.1. Цель

Дать участникам Екатеринбурга минимальный публичный рынок коллабораций внутри Telegram без Mini App, отдельного сайта и сложной инфраструктуры.

### 3.2. Продуктовая гипотеза

Если участник может быстро оформить понятную карточку, найти релевантные предложения по трём простым фильтрам и безопасно раскрыть контакт только после принятия отклика, то часть предложений дойдёт до реального сотрудничества.

### 3.3. Режим первого запуска

Автор проекта вручную отправляет ссылку на бота знакомым и небольшому числу других людей. Ожидаются единицы или десятки пользователей, но технический лимит пользователей не вводится.

Первый запуск не требует продуктовой аналитики, формальной программы пилота, числовых go/no-go-порогов, SLA или подготовки к масштабированию. Решение о продолжении принимается автором по фактическому интересу и прямой обратной связи.

Приоритет реализации — как можно раньше получить работающий пользовательский цикл. Возможности, которые не помогают пройти этот цикл и не закрывают непосредственный риск утечки секрета, потери авторитетных данных или раскрытия контакта, не блокируют запуск.

## 4. Первый рынок и роли

### 4.1. География

В MVP поддерживается только Екатеринбург. Город не выбирается в wizard и хранится как каноническое значение `ekaterinburg`.

Другие города не публикуются и не показываются в ленте.

### 4.2. Типы профиля

Канонический enum `ProfileType`:

| Значение | Отображение |
|---|---|
| `blogger` | Блогер |
| `telegram_channel` | Telegram-канал |
| `venue_or_brand` | Заведение или бренд |

`Фотограф`, `специалист`, `организатор мероприятий` и `другое` не являются отдельными типами профиля MVP.

### 4.3. Роли в конкретной карточке

- Автор — владелец профиля, создавший карточку.
- Кандидат — владелец другого профиля, отправивший отклик.
- Принятый партнёр — кандидат с откликом `accepted`.
- Администратор — Telegram-пользователь, чей ID находится в конфигурационном allowlist.

Один человек может быть автором в одной карточке и кандидатом в другой.

## 5. Канонические справочники

### 5.1. Формат коллаборации

`CollaborationFormat` содержит семь значений:

| Значение | Отображение |
|---|---|
| `advertising_integration` | Рекламная интеграция |
| `barter` | Бартер |
| `joint_giveaway` | Совместный розыгрыш |
| `joint_content` | Совместный контент |
| `mutual_pr` | Взаимный PR |
| `event` | Мероприятие |
| `other` | Другое |

Формат является только меткой и фильтром. Все семь форматов используют одинаковые поля и один wizard. Специализированных `GiveawayDetails` и перехода в Giveaway Bot в MVP нет.

### 5.2. Кого ищет автор

`TargetProfileType` содержит значения `blogger`, `telegram_channel`, `venue_or_brand` и `any`.

Карточка выбирает ровно одно значение. `any` означает любой тип профиля MVP.

### 5.3. Тематики

`Topic` содержит:

- `lifestyle` — Lifestyle;
- `food` — Еда и рестораны;
- `beauty` — Красота;
- `travel` — Путешествия;
- `city` — Город;
- `events` — События;
- `family` — Семья;
- `sport` — Спорт;
- `business` — Бизнес;
- `other` — Другое.

Профиль и карточка выбирают от одной до трёх тематик.

### 5.4. Публичные площадки

`PlatformType` содержит `telegram`, `instagram`, `vk`, `tiktok`, `youtube`, `website` и `other`.

Профиль обязан иметь хотя бы одну публичную площадку. Фильтра по площадке в MVP нет.

## 7. Профиль

### 7.1. Отложенное создание

`/start` не запускает обязательную анкету. Пользователь видит меню и может открыть ленту без профиля.

Профиль обязателен при первой попытке:

- создать карточку;
- отправить отклик.

После завершения профиля бот возвращает пользователя в исходное действие.

### 7.2. Поля

| Поле | Правило | Видимость |
|---|---|---|
| Тип профиля | одно значение `ProfileType` | публично |
| Название | 2–100 символов | публично |
| Тематики | 1–3 значения `Topic` | публично |
| Описание | обязательно, 10–500 символов | публично |
| Площадки | минимум одна | публично |
| Размер аудитории | необязательное целое число ≥ 0 для площадки | публично |
| Контакт | 3–200 символов | только после принятия |
| Город | всегда Екатеринбург | публично |

Публичная площадка и закрытый контакт — разные данные. Ссылка на канал, блог или сайт может быть видна до match; адрес для прямой связи скрыт.

### 7.3. Telegram-канал

Для типа `telegram_channel` бот сначала предлагает нативно выбрать канал. Если Telegram не вернул username либо пользователь отказался от выбора, доступен ручной ввод публичной ссылки.

Нативный выбор не доказывает, что бот состоит в канале, и не даёт Collaboration Bot право публиковать туда.

### 7.4. Один профиль в интерфейсе

MVP разрешает создать один активный профиль на Telegram-пользователя. Все карточки и отклики ссылаются на `profile_id`, а не напрямую на Telegram ID.

Схема данных допускает несколько профилей на одного пользователя, но команды создания второго профиля и переключения отсутствуют.

Все поля активного профиля можно редактировать. Изменения не отменяют и не перевалидируют уже созданные карточки или отправленные отклики: соответствие типа кандидата проверяется в момент отправки отклика. Последующие публичные и pairwise-проекции используют актуальные данные профиля, но закрытый контакт по-прежнему доступен только конкретной принятой паре.

### 7.5. Блокировка и удаление

Заблокированный пользователь может открыть `/start` и `/help`, посмотреть свою историю и уже раскрытые ему accepted-контакты. Любая пользовательская mutation — создание или изменение профиля/карточки, публикация, отклик, отзыв, решение или completion report — запрещена единым правилом.

Удаление собственного профиля не входит в MVP. Запрос на удаление данных обрабатывается владельцем продукта вручную; контакт администратора должен быть доступен через `/help`.

## 8. Карточка коллаборации

### 8.1. Поля

| Поле | Правило |
|---|---|
| Формат | одно значение `CollaborationFormat` |
| Кого ищут | одно значение `TargetProfileType` |
| Тематики | 1–3 значения `Topic` |
| Название | 5–100 символов |
| Что предлагает автор | 10–1000 символов |
| Что ожидает автор | 10–1000 символов |
| Количество мест | целое число 1–10 |
| Дедлайн откликов | будущая календарная дата, не позднее 90 дней; отклики принимаются до 23:59:59.999 `Asia/Yekaterinburg` включительно |
| Дата проведения | необязательная календарная дата; не раньше календарной даты дедлайна |
| Город | всегда Екатеринбург |

Карточка получает внутренний ID и отдельный непрозрачный публичный токен. В публичные кнопки и deep links внутренний ID не включается.

### 8.2. Wizard

Wizard выполняет шаги:

1. формат;
2. кого ищут;
3. тематики;
4. название;
5. предложение автора;
6. ожидание от партнёра;
7. количество мест;
8. дедлайн;
9. необязательная дата проведения;
10. предпросмотр;
11. публикация.

На каждом шаге доступны `Назад` и `Отмена`. `Отмена` транзакционно удаляет никогда не публиковавшийся `draft`, его темы и wizard-session; такой draft не переводится в `cancelled` и не попадает в историю карточек. После перезапуска бот предлагает продолжить сохранённый flow либо удалить его.

### 8.3. Предпросмотр

Предпросмотр использует тот же render, что карточка в боте и showcase-пост, с учётом разных лимитов Telegram.

Публикация запрещена, если итоговый render не помещается в лимит целевого сообщения.

### 8.4. Редактирование

Автор может изменить все поля `draft`.

Условия `published` можно изменить только пока по карточке никогда не было отправлено ни одного отклика. Наличие `pending`, `accepted`, `rejected`, `withdrawn` или `closed` блокирует изменение условий.

После первого отклика автор может отменить карточку или создать новую карточку на основе старой. Автоматического копирования в MVP нет.

## 9. Лента и просмотр

### 9.1. Вход

Лента доступна без профиля. Отправка отклика требует профиль.

### 9.2. Фильтры

Пользователь может независимо выбрать:

- тип искомого партнёра;
- формат;
- тематику.

Каждый фильтр допускает значение `Любой`.

Между выбранными измерениями действует AND. Формат требует точного совпадения, тема — наличия в `collaboration_topics`. Выбранный тип партнёра включает карточки с таким `target_profile_type` и со значением `any`; `Любой` не ограничивает измерение.

### 9.3. Выдача

Карточки сортируются по `published_at DESC, id DESC`.

Из выдачи исключаются:

- карточки самого пользователя;
- все статусы, кроме `published`;
- карточки с заполненными местами;
- карточки с прошедшим дедлайном;
- карточки, на которые текущий профиль уже откликался;
- карточки, уже показанные в текущей browse-сессии.

Browse-сессия заканчивается при изменении фильтров, явном действии `Показать сначала` либо через 24 часа неактивности.

Если подходящих карточек нет, бот предлагает изменить фильтры или начать выдачу сначала.

### 9.4. Deep link

Showcase-кнопка открывает `/start c_<token>` и показывает конкретную карточку независимо от текущей browse-сессии.

Для недоступной карточки показывается её безопасный публичный результат: `предложение закрыто`, `срок истёк` или `предложение недоступно`. Причина модерации и внутренние ошибки не раскрываются.

## 10. Отклики и заполнение мест

### 10.1. Отправка

Отклик содержит:

- ссылку на профиль кандидата;
- сообщение длиной 10–500 символов;
- снимок версии карточки, на которую он отправлен.

Один профиль может иметь не более одного отклика на карточку. Повторный отклик после `withdrawn` или `rejected` в MVP запрещён.

Нельзя откликнуться:

- на собственную карточку;
- без активного профиля;
- заблокированному пользователю;
- на карточку не в `published`;
- если тип профиля кандидата не совпадает с `target_profile_type`, кроме карточек с `any`;
- после дедлайна;
- когда места заполнены;
- пока состояние showcase-синхронизации запрещает новые действия.

### 10.2. Получение автором

Автор получает уведомление с публичными данными профиля и текстом отклика. Закрытый контакт кандидата не показывается.

Для `pending` доступны `Принять` и `Отказать`.

### 10.3. Решение

Принятие выполняется атомарно:

- повторная обработка того же callback возвращает уже сохранённый результат;
- число `accepted` никогда не превышает `slots_total`;
- при заполнении последнего места карточка становится `matched`;
- оставшиеся `pending` становятся `closed`;
- контакты раскрываются только автору и конкретному принятому кандидату.

Каждая принятая пара получает два поля второй стороны: кликабельную Telegram-ссылку, если у пользователя есть username, и сохранённое закрытое поле `Контакт`. Отсутствие Telegram username не мешает match. Принятые партнёры в multi-slot-карточке не получают контакты друг друга.

Отказ переводит только выбранный отклик в `rejected`.

Кандидат может отозвать только `pending`-отклик; он становится `withdrawn`.

Принятый отклик нельзя отменить или заменить через self-service MVP. Если договорённость сорвалась, стороны фиксируют `не состоялось`.

### 10.4. Досрочное завершение набора

Если принят хотя бы один партнёр, автор может завершить набор до заполнения всех мест. Карточка становится `matched`, а все оставшиеся `pending` — `closed`.

## 11. Состояния

### 11.1. Collaboration

| Из | Событие | В | Кто |
|---|---|---|---|
| — | начало wizard | `draft` | автор |
| `draft` | отмена wizard | —, draft удалён | автор |
| `draft` | запуск публикации | `publishing` | автор |
| `publishing` | showcase-пост подтверждён | `published` | система |
| `publishing` | дедлайн истёк до первого send либо known success получен уже после дедлайна | `expired` | система |
| `publishing` | permanent/исчерпанный known failure или ambiguous outcome | `publication_failed` | система |
| `publication_failed` | latest attempt = `known_failed`, `message_id` отсутствует, нет unresolved `ambiguous`, `occurredAt <= response_deadline_at` | `publishing` | автор/администратор |
| `publication_failed` | найденный пост подтверждён reconciliation-проверкой при `now <= response_deadline_at` | `published` | администратор/система |
| `publication_failed` | latest attempt = `known_failed`, пост отсутствует, нет unresolved `ambiguous`, `now > response_deadline_at` | `expired` | система |
| `publication_failed` | ambiguous outcome безопасно сверен после дедлайна: найденный пост привязан либо отсутствие/удаление доказано | `expired` | администратор/система |
| `publishing` или `publication_failed` | автор заблокирован | `cancelled` | администратор |
| `published` | заполнено последнее место | `matched` | система |
| `published` | автор завершил набор при ≥1 accepted | `matched` | автор |
| `published` | дедлайн, есть accepted | `matched` | система |
| `published` | дедлайн, accepted нет | `expired` | система |
| `published` или `matched` | автор отменил | `cancelled` | автор |
| `matched` | автор завершил сотрудничество | `completed` | автор |
| `published`, `matched`, `completed`, `cancelled` или `expired` | модерационное скрытие | `hidden` | администратор |
| `hidden` | новый showcase-пост подтверждён | значение `hidden_from_status` | администратор/система |

`completed`, `cancelled` и `expired` терминальны для продуктовых действий; admin hide/restore является исключением уровня видимости. `hidden` хранит `hidden_from_status` и причину модерации. Во время restore карточка остаётся `hidden` до известного успеха Telegram; затем восстанавливается прежний бизнес-статус. Любой restore требует активного автора, а возврат в `published` дополнительно требует неистёкшего дедлайна. Если дедлайн наступил во время hide, система меняет сохранённый бизнес-статус на `matched` или `expired`, не возвращая карточку в ленту.

Отмена `published` или `matched` атомарно закрывает все `pending`-отклики и создаёт уведомления. Уже `accepted`-отклики и раскрытые контакты не изменяются.

### 11.2. Application

| Из | Событие | В |
|---|---|---|
| — | отправка | `pending` |
| `pending` | принятие | `accepted` |
| `pending` | отказ автора | `rejected` |
| `pending` | отзыв кандидата | `withdrawn` |
| `pending` | набор закрыт, карточка скрыта, отменена или истекла | `closed` |

`accepted`, `rejected`, `withdrawn` и `closed` терминальны.

### 11.3. Действия с терминальной карточкой

- Терминальная карточка не возвращается в ленту.
- Deep link продолжает давать безопасный статус, кроме `hidden`.
- Принятые контакты не отзываются: Telegram-сообщение уже могло быть прочитано.
- Исторические записи не удаляются и используются для аналитики.

## 12. Later: завершение и факт сотрудничества

Этот раздел не входит в первый запуск. Он сохраняет продуктовый замысел для возможного продолжения после подтверждённого интереса пользователей.

Автор переводит `matched` в `completed` действием `Завершить коллаборацию`.

После этого бот отдельно спрашивает автора по каждому принятому партнёру и самого партнёра:

- `Состоялось`;
- `Не состоялось`;
- `Ответить позже`.

`Ответить позже` не создаёт итоговый ответ и допускает ровно одно durable-напоминание не ранее чем через 72 часа. Итоговый ответ атомарно отменяет ещё не взятое runner-ом напоминание; после итогового ответа новое напоминание не создаётся.

Пара считается подтверждённой состоявшейся коллаборацией, только если автор и конкретный партнёр ответили `Состоялось`.

Противоречащие ответы сохраняются для аналитики, но не запускают арбитраж и не публикуются в профиле.

Рейтинга, комментария и публичной репутации в MVP нет.

## 13. Showcase-канал

### 13.1. Назначение

Один Telegram-канал является публичной витриной. Бот должен иметь права публиковать, редактировать и удалять сообщения.

### 13.2. Первичная публикация

Карточка становится `published` и появляется в ленте только после того, как Telegram вернул известный `message_id` showcase-поста, и при этом дедлайн ещё не истёк. Если дедлайн истёк во время сетевого вызова, известный пост привязывается, но карточка сразу становится `expired`, не попадает в ленту, а пост получает закрытый статус.

До этого карточка остаётся `publishing` и не принимает отклики.

Известная временная ошибка повторяется ограниченно, пока карточка остаётся `publishing`; постоянный отказ или исчерпание попыток переводит публикацию в `publication_failed`. Безопасный retry до включительного дедлайна разрешён только для доказанного `known_failed` без `message_id` и без unresolved `ambiguous`; после дедлайна такая карточка автоматически становится `expired` без Bot API call. Неоднозначный результат не повторяется автоматически, чтобы не создать дубликат, и не истекает автоматически до сверки канала. Если пост найден, reconciliation проверяет контроль над известным `message_id`, привязывает его и в transaction известного результата переводит карточку в `published` при `now <= response_deadline_at` либо в `expired` при `now > response_deadline_at`. Если orphan-пост удалён или доказано не созданным, администратор может подтвердить новую попытку только при `occurredAt <= response_deadline_at`; после него карточка становится `expired` без новой отправки.

### 13.3. Синхронизация

Пост содержит:

- формат;
- название;
- кого ищут;
- тематики;
- предложение и ожидание;
- оставшиеся и общие места;
- дедлайн;
- текущий публичный статус;
- кнопку deep link в карточку.

После принятия партнёра обновляется остаток мест. После `matched`, `completed`, `cancelled` или `expired` пост остаётся и редактируется со статусом без активной кнопки отклика.

`hidden` удаляет пост. Восстановление создаёт новый пост и сохраняет новый `message_id` только после известного успеха delete или подтверждённого отсутствия старого поста. Пока delete не сверен, restore запрещён во избежание двух постов.

Известные ошибки edit/delete повторяются ограниченно. Ошибка синхронизации не откатывает принятое бизнес-решение, но фиксируется и показывается администратору.

## 14. Модерация

### 14.1. Выбранная политика

В MVP нет:

- премодерации;
- пользовательской кнопки жалобы;
- дневных или активных продуктовых лимитов;
- автоматического антиспам-скоринга.

Это осознанный риск небольшого первого запуска с ручным распространением.

### 14.2. Действия администратора

В первом запуске администратор может найти карточку и скрыть её из бота и showcase-канала. Это единственное обязательное действие модерации.

Restore, block/unblock, каскадная обработка связанных сущностей, специальные правила конкурентного block/accept и интерфейс инцидентов относятся к Later. Описанная ниже расширенная политика сохраняется как проектный backlog, но не является gate первого запуска.

Блокировка:

- запрещает новые изменяющие действия пользователя;
- отменяет его незавершённые `publishing`/`publication_failed`-карточки; если поздний ответ Telegram вернёт `message_id`, пост не делается публичной карточкой и удаляется;
- скрывает его активные `published`- и `matched`-карточки;
- переводит их pending-отклики в `closed`;
- переводит в `closed` все `pending`-отклики, отправленные его профилями на чужие карточки;
- удаляет соответствующие showcase-посты;
- не меняет ранее принятые отклики и не пытается отозвать раскрытые контакты.

При принятии отклика статус кандидата проверяется повторно в той же serialized transaction. Если block зафиксирован первым, отклик закрывается и контакт не раскрывается. Если accept зафиксирован первым, он остаётся `accepted`, а последующий block не пытается отозвать уже возникшее право на контакт. Последующая разблокировка не воскрешает `closed`.

Каждая изменяющая admin-команда, включая moderation и publication reconciliation, в той же transaction атомарно добавляет append-only operator audit: actor, цель, action type, обязательную внутреннюю причину длиной 1–500 символов, безопасные before/after state, command ID и время. Причина не показывается публично и не попадает в пользовательские уведомления.

## 17. Later: аналитика

Аналитика не входит в первый запуск и не является условием публикации бота. Раздел сохраняет возможный контракт на случай продолжения проекта.

### 17.1. События

Минимальный `ProductEventType`:

- `bot_started`;
- `profile_started`;
- `profile_completed`;
- `collaboration_draft_started`;
- `collaboration_published`;
- `collaboration_viewed`;
- `application_submitted`;
- `application_accepted`;
- `collaboration_matched`;
- `completion_reported`;
- `collaboration_bilateral_confirmed`;
- `collaboration_hidden`;
- `user_blocked`.

Повтор Telegram update или callback не создаёт второй продуктовый event с тем же idempotency key.

`collaboration_viewed` фиксируется только после известного успешного `sendMessage` или `editMessageText`, который показал пользователю публичную карточку. Его idempotency key связывает конкретные ingress command и collaboration; ошибка или неоднозначный результат Telegram не считаются просмотром.

### 17.2. Данные

В event разрешены:

- тип события;
- UTC-время;
- внутренние IDs пользователя, профиля, карточки и отклика;
- безопасные enum/числовые атрибуты;
- idempotency key.

В event и логах запрещены BOT_TOKEN, deep-link token, закрытый контакт, полный текст карточки и полный текст отклика.

### 17.3. Отчёт

Внешняя аналитическая система не требуется. Воронка строится read-only SQL-запросом по SQLite.

## 18. Ошибки и пользовательское поведение

- Устаревшая или повторная кнопка показывает сохранённый текущий результат.
- Кнопка другого пользователя не выполняет действие.
- После рестарта незавершённый wizard можно продолжить.
- Неизвестный результат публикации не приводит к автоматической повторной отправке.
- Временная ошибка обычного уведомления не изменяет бизнес-состояние.
- Длинный или некорректный ввод отклоняется на текущем шаге без потери черновика.
- Заблокировавший бота пользователь не ломает обработку остальных доставок.
- Одновременное принятие последнего места даёт один `accepted` и детерминированный отказ второму действию.
- Утрата прав в showcase-канале блокирует новые публикации, но не чтение уже сохранённых карточек и откликов.
- Групповые и channel updates не участвуют в пользовательских flows.

## 21. Трассировка и изменение scope

Для первого запуска Technical Design и implementation plan обязаны сопоставить каждому `LFR-*` и `LAC-*`:

- application use case;
- таблицы и ограничения;
- Telegram entrypoint;
- failure policy;
- автоматический и/или ручной тест;
- implementation slice.

Требование нельзя считать реализованным только по наличию UI-текста. Для готовности должны одновременно существовать бизнес-инвариант, durable state и проверка соответствующего `LAC-*`.

Исторические `FR-*`/`AC-*`, которые не представлены в `LFR-*`/`LAC-*`, являются Later backlog и не блокируют первый запуск.

Новая возможность сначала классифицируется как MVP, Later или Out of scope. Формулировки `может`, `по возможности` и `обсуждалось` не создают обязательства реализации.
